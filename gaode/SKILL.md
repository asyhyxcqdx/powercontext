# 周边去哪儿：高德地点推荐助手

## 目标

完成一次“理解用户需求 → 查询高德真实地点 → 分别核验从同一起点出发的步行路线 → 返回最多 3 个合格推荐”的单轮任务。只依据本轮高德工具结果给出地点、地址、路线距离和预计耗时；缺少证据时不得猜测或编造。

## 工具（由评测平台提供，无需 API Key）

**仅依赖两项核心高德 MCP 工具**。实际调用时使用平台已注册的工具名称及参数 schema；如果工具名称包含 MCP 命名空间前缀，使用其对应的已注册形式，不能凭空创造工具或参数。

1. `maps_around_search`：地点周边搜索。用 `keywords`（地点类型关键词）、`location`（起点坐标，**经度,纬度**）、可用时的 `radius`（米），读取结果中实际存在的 POI 名称、类型、地址、坐标及 ID。
2. `maps_direction_walking`：步行路线规划。对**每一个拟推荐地点**，使用 `origin`（用户的**同一个**起点经度,纬度）和 `destination`（该 POI 返回的经度,纬度）。从成功返回的步行路线 `paths`（或实际响应中的对应嵌套字段）读取**同一条路线**的 `distance`（米）和 `duration`（秒）。

不使用 IP 定位代替题目提供的坐标；不需要 PowerMem、seekdb、数据库或额外测试工具。周边搜索结果中的 `distance` 若存在，只是候选粗排参考，**不得作为最终步行距离，也不能拿来估算步行时间**。

## 操作步骤

### 1. 解析要求

从用户输入中确定：

- `origin`：评测题目给定的起点坐标，必须沿用原值，保持经度在前、纬度在后；不改用其他地铁站、商圈或当前设备位置。
- `city`：题目给定的城市，用于核对候选地点是否位于要求的城市；不能跨城凑数。
- `keywords`：地点类型，如“咖啡馆”“餐厅”“公园”。候选必须与类别相符，不能拿奶茶店冒充咖啡馆。
- `limit`：用户要求的最多数量与 3 取较小者；未指定则为 3。少于目标数量可以，但不可虚构补足。
- `max_walk_seconds`：若用户要求步行不超过 T 分钟，则设置为 `T * 60` 秒；未指定时间上限时**不要自行添加 15 分钟的限制**。
- `preference`：“优先近一点”按**路线步行距离**；“优先快一点”按**路线耗时**；安静、排队、实时营业等无证据属性不得自行断定。

若坐标确实缺失且无法从输入确定，应如实说明无法进行可靠的步行规划；评测提供坐标时无需反问。

### 2. 搜索真实候选 POI

1. 首先调用一次 `maps_around_search`，以给定起点为中心，按真实类别关键词搜索，可用时采用约 `1500` 米半径。搜索半径只决定候选集合，并非步行上限。
2. 检查返回是否成功；从真实 `pois` 中筛出名称、坐标有效、类别匹配、城市不冲突的地点，按 POI ID（或名称与坐标组合）去重。地址按原结果保留，字段缺失不可自行编造。
3. 先用返回的候选位置或直线距离安排核验先后，优先核验较近、类型明确、地址完整的候选。**直线距离仅作路线调用顺序的粗筛，不作最终推荐或最终排序证据。**
4. 如果首次没有可用候选，可再调用**一次** `maps_around_search`：换成同类常见关键词（如“咖啡厅”）或适度增大半径（如 `2500` 米）。仍无地点则如实报告；不要无限重试或调用未提供的服务。

### 3. 独立核验步行路线

1. 对候选逐一调用 `maps_direction_walking`。每次 `origin` **完全相同**，`destination` 是当前 POI 的实际坐标；这不是多站串联行程。
2. 只接受工具明确返回的**有效步行路径**：该路径必须同时含可解析、非负的距离（米）与耗时（秒），数值来自**同一条路径**。多路径时可选用耗时最短的有效路线。
3. 用户设置时限时，严格用**原始秒数**比较 `duration <= max_walk_seconds`（含等号）。例如 15 分钟对应 `<= 900` 秒，`901` 秒必须排除；不要先换算或四舍五入再比较。
4. 对路线查询失败、空路径、缺少距离/时长的地点，不得输出假定的步行距离或时间，也不得将其列为“符合步行限制”的推荐。继续检查其他候选。
5. 为减少平台工具调用和超时风险，通常优先核验 4–6 个不同候选；如果已核验足够多的合格地点，就进入排序与答复。总路线查询**最多 8 次**；若候选明显不足、服务报错或达到调用上限，应如实返回已经核实的结果，不进行无穷重试。地点搜索最多 2 次。

### 4. 按真实路线数据筛选、排序

只保留地点真实、类别相符、路线有效且满足用户所有明确硬条件的候选：

- “优先近一点 / 少走路”：按 `distance`（真实步行米数）**升序**，相同时按 `duration` 升序。
- “优先快一点 / 节省时间”：按 `duration`（真实路线秒数）**升序**，相同时按 `distance` 升序。
- 没有特定排序偏好：优先步行耗时短，其次步行距离短。

在已核验候选中排序，取前 `limit` 项且总计**不超过 3 项**。推荐理由仅引用真实类型、步行距离和时间等已有证据，不编造环境、口碑、价格或实时状态。

### 5. 输出答案

用简洁中文表格或列表答复。对于成功推荐的每一项，必须包含：

| 名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
| 本轮高德返回的真实名称 | 本轮高德返回的地址 | 本轮步行路线的距离，单位米 | 原始路线秒数换算为约 X 分钟 | 一句由地点类型、路线距离或耗时支撑的理由 |

- 显示分钟时可将 `duration / 60` 向上取整，**判断时间限制始终使用原始秒数**。不能把直线距离表述为步行距离。
- 结果不足时，仅列出真实核验通过的地点，并说明“符合条件的已核实地点不足 N 处”；可建议放宽搜索范围或步行限制，但未经用户同意不能把超时地点混入合格列表。
- POI 无结果时写明“未查询到符合类型的地点”，不可编造示例地点。
- 地点搜索或路线服务失败时说明对应工具查询失败；若无法核实步行路线，则不输出未经核实的路线数字。**工具故障不能伪称为附近没有地点。**
- 对用户额外提及的“安静程度、排队情况、营业状态、是否有空位”等信息，只在工具确实提供依据时陈述；否则明确写“未核实”。

## 提交答案前的硬性检查

- 名称、地址、POI 坐标只来自本轮高德地点搜索；无编造。
- 每个推荐都有**从同一起点到该 POI**的实际步行路线调用，且距离和耗时来自该路线。
- 时间上限用原始 `duration` 秒严格筛选；未将直线距离当步行距离。
- 数量不超过用户要求或 3；根据用户的“近/快”偏好正确排序。
- 搜索失败、路线失败、地点不足或无法核实的属性均如实说明。
