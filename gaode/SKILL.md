# 周边去哪儿：高德地点与步行路线推荐

## 目标与不可违反的规则

根据用户提供的**城市、同一个起点坐标（经度,纬度）和自然语言要求**，调用高德 MCP 搜索真实 POI（兴趣点），然后对每个拟推荐的 POI **独立调用步行路径规划**。返回不超过用户指定数量、且最多 3 个的地点。每项提供地点名称、地址、**高德步行路线距离（米）**、**高德预计步行时间（分钟）**和有依据的推荐理由。

必须满足：

1. **先工具查询，再回答。** 绝不凭常识、记忆或模型猜测编造地点、地址、坐标、路线、距离、时长；不得声称执行了未发生的工具调用。
2. **路线是硬门槛。** 只有已从 `maps_direction_walking` 成功取得该地点步行路线距离和耗时的 POI，才可作为“符合步行条件”的推荐。POI 搜索返回的 `distance` 通常是直线距离，**绝不能替代步行距离或步行耗时**；也不得以直线距离/假定步速推导步行耗时。
3. **执行明确约束。** 例如步行“15 分钟内”表示原始路线耗时 `duration <= 900` 秒（含边界）；先按秒比较，再按显示格式取整。超时的地点绝不列入符合条件的推荐。
4. **同起点、非多站。** 每一条步行路线的 `origin` 都是用户提供的相同起点，`destination` 是当前 POI 的真实坐标；不能将上一个地点当下一个地点的起点，也不需要设计连逛路线。
5. **最多三项，可少不可凑。** 用户指定 N 家时取 `min(max(N,0),3)`；未指定时最多 3 家。有效候选不足就少推荐甚至零推荐，并解释原因，绝不补造结果。
6. **事实与偏好分离。** 店铺是否安静、是否排队、是否正在营业、是否有座位、环境是否适合学习等，若高德返回数据无法证实，明确说“未核实”，不能写成确定事实。不能把模型喜好当作真实店铺特征。

## 工具与参数

运行环境由评测平台提供高德 MCP；直接使用已注册的工具，不要求用户提供 API Key、安装依赖、登录账号或自行连接数据库。优先使用工具实际暴露的完整名称（可能带有 MCP 服务前缀），参数以当前工具 schema 为准。

- **周边地点搜索（首选）**：`maps_around_search`，传入 `keywords`（如 `咖啡馆`、`中餐厅`、`公园`）、`location`（**经度,纬度**），以及可用时的 `radius`（米）。返回 POI 的 `id`、`name`、`type`、`address`、`location` 等。
- **步行路线查询（必做）**：`maps_direction_walking`，传入 `origin`=`起点经度,纬度`、`destination`=`POI经度,纬度`；从成功返回的 `paths`（或嵌套的 `route.paths`）中读取同一条有效路线的 `distance`（米）和 `duration`（秒）。若有多条有效步行方案，可选耗时最短者，但距离与耗时必须来自同一条方案。
- **必要时的补充工具**：`maps_text_search(keywords, city)` 用于周边检索无匹配后的同城补查；`maps_search_detail(id)` 用于核实某个已搜索到的 POI 的地址、类别和坐标。不要把这两种工具作为绕过步行路线查询的手段。

## 逐步执行

### 第一步：解析用户条件

从用户需求提取并在内部记录：

- `city`：用户明确指定的城市；不能自行切换到另一座城市。
- `origin`：题目提供的起点精确坐标，按 **经度,纬度** 原样传给高德工具，始终保持一致；已有坐标时不再用 IP 定位或名称模糊地理编码覆盖它。若未提供坐标但提供明确地址且工具可用，可用地理编码确认；起点确实无法确定时只询问必要信息，不编造位置。
- `category / keywords`：用户真正需要的 POI 类型。例如“咖啡馆”不要混为奶茶店或一般餐饮；“公园”不要混成商场。
- `max_walk_seconds`：若有时长上限，分钟乘以 60 转为秒；“以内/不超过”采用 `<=`。无时限则不私自捏造 15 分钟限制。
- `limit`：用户指定的上限与 3 取较小者；未给出按 3；如“最多两家”则最多 2 家。
- `preferences`：如“优先近一点”“尽量省时间”“安静”“经济实惠”等，区分可用客观数据验证的条件与未核实主观条件。

### 第二步：搜索并检查真实地点

1. 调用 `maps_around_search`，以用户起点为搜索中心，`keywords` 与 POI 需求一致。通常从约 1500–2000 米半径开始；搜索半径只用于**收集候选**，不是步行时长合格的证明。
2. 若搜索失败或没有有效 POI，可在合理范围内调整同义关键词、适度扩大半径（例如不超过约 3000 米）重试一次；必要时用 `maps_text_search` 按用户指定城市补查。搜索结果仍需以实际步行路线过滤，且不能把其他城市的同名地点混入。
3. 对 POI 按 `id` 去重（若无 `id`，结合准确名称与坐标去重），核对类型是否确实匹配、坐标是否完整、名称是否可信，并保留高德原样返回的地址与 POI 信息。排除类别明显不符、坐标缺失或疑似错误的条目。
4. 若地址缺失，可调用 `maps_search_detail` 查询该 POI；仍无有效地址时优先选择信息完整的其他候选，不能自行拼写地址或推断楼层门牌。
5. 用 POI 搜索中的直线距离（若提供）**仅作为安排路线核验顺序的粗筛依据**，不可据此决定最终距离排名或回答中的“步行距离”。优先检查相对靠近、类别匹配的约 8 个不同候选；若合格不足，视剩余结果及工具状况继续检查，通常不超过 12 个，避免仅检查 3 个就仓促得出结论。

### 第三步：逐个规划独立步行路线并严格筛选

对每个待核验的候选调用 `maps_direction_walking(origin, destination)`：

1. `origin` 必须是相同的用户起点，`destination` 必须是该候选 POI 的准确高德坐标。检查返回是否成功，是否存在具体步行方案，以及所选方案是否同时含有可解析的、非负的 `distance` 与 `duration`。读取路线信息的原始单位：距离米、耗时秒。
2. 工具明确失败、返回空路线、路线字段缺失、值不合法或仅有直线距离时，不得将该 POI 宣称为步行可达且符合时长；保留为“路线未核实”并尝试其他候选。
3. 若用户设置步行上限，使用未四舍五入的 `duration_seconds` 做硬过滤：`duration_seconds <= max_walk_seconds` 才合格；即使显示时看起来都是“约 15 分钟”，901 秒也**不**符合 15 分钟内。
4. 保存每个通过的候选的 `POI id/名称/地址/坐标`、`同一起点`、`所选步行方案`、`distance_m`、`duration_seconds`。最后回答的数字必须与对应这一次工具调用及同一条路线保持一致，不得把不同地点、不同路线的数据串用。

### 第四步：按偏好排序并生成推荐

仅在**类别匹配、真实地点、有可验证步行路线、满足所有明确硬约束**的候选中排序：

- 用户说“**优先近一点**”“走得短一点”：按实际**步行距离 `distance_m` 升序**，距离相同时按 `duration_seconds` 升序；不可按 POI 直线距离排序。
- 用户说“**优先快一点**”“用时最短”：按实际**步行耗时 `duration_seconds` 升序**，相同时按步行距离升序。
- 没有明确偏好：优先步行耗时短，其次距离短；只有在存在高德可核实的额外偏好证据时才据此调整次序。
- 只取排序后的前 `limit` 个，不超过 3 个。用实际的类别匹配、路线距离或时间等事实写一句理由；“氛围安静”“人少”“评分最高”“现正营业”等没有明确数据支撑时不得写入。

### 第五步：清晰回答（中文，简洁）

先说明起点（仅使用用户给出的名称或坐标）和已实际采用的硬条件，然后使用列表或表格。默认格式：

| 推荐 | 地点名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- | --- |
| 1 | [高德 POI 原始名称] | [高德地址] | [路线 distance 米] | 约 [将路线 duration 秒向上取整为分钟] 分钟 | [与类别/步行距离/耗时相符的客观依据] |

具体要求：

- 距离显示为整数米或适度换算公里；时间由路线秒数换算为分钟，建议向上取整；**先用原始秒数判断合格，再格式化显示**，不能让取整掩盖超时。
- 同一句中避免把“附近搜索半径”“直线距离”和“步行路线距离”混为一谈；逐项对应正确 POI。
- 如果用户要求“安静”“营业中”等缺乏工具证明的信息，末尾添加：“安静程度/实时营业状态等未核实，建议出发前确认。”如果已经有真实、可核实的信息则准确引用，不做额外断言。
- 合格推荐少于所要求数量：仍按真实结果呈现，并补充“当前已核实且符合条件的地点只有 X 处”，必要时说明受限于距离、时长、地址或路线数据；可以建议放宽时间/类别/搜索范围，但**不可擅自放宽条件后将不合格地点列为合格**。
- 搜索确实无结果：直接说明“未查到符合该类型的地点”，可建议更换关键词或扩大范围，**不展示虚构表格行**。
- 高德搜索或路线工具异常：明确指出“地点搜索失败”或“步行路线查询失败，无法核实距离与时间”，不输出未经核验的数字，也不把服务故障谎称为范围内没有地点。

## 完成前自检

只要有任一项不满足，就必须修正答案或删掉不合格推荐：

- [ ] 全部地点来自本次高德 POI 查询，地点名称、地址、类别有据可查。
- [ ] 每个推荐都实际调用了 `maps_direction_walking`，并有对应、有效的距离和时间。
- [ ] 每次路线使用相同起点与该 POI 的终点，均不是多站串联。
- [ ] 原始耗时（秒）满足用户要求；未将直线距离/估算耗时当作路线数据。
- [ ] 数量 `<= min(用户上限,3)`；排序符合距离或时间优先偏好。
- [ ] 无结果、结果不足、工具错误和未核实的主观条件均得到诚实说明。
- [ ] 输出简洁，包含名称、地址、步行距离、步行时间和一句有依据的推荐理由。
